# 대시보드 디자인 시스템 (10단계 기획, 2026-11-16 확정)

기획서 11장 "재생 시뮬레이션 대시보드"를 Next.js(프론트엔드) + FastAPI(백엔드)로 만들기 전에 정하는
디자인 기준이다. 0장의 제안대로 확정했고 11단계 구현(`app/`)에 적용했다.
화면 미리보기: [`preview.html`](preview.html) (브라우저로 열기).

## 0. 결정 (모두 제안대로 확정)

| 항목 | 제안 | 대안 |
|---|---|---|
| 언어 | JavaScript (사용자 지정). 파일은 `.jsx`, 데이터 형식은 JSDoc 주석 | TypeScript |
| 차트 라이브러리 | Apache ECharts (canvas, 수천 점 실시간 추가에 강함, 툴팁·십자선 내장) | Recharts (SVG, 단순하지만 점이 많으면 느림) |
| 재생 방식 | 시나리오(시작 구간 × 재학습 옵션)를 미리 계산해 두고, 브라우저 타이머가 shot을 하나씩 진행 | 서버가 SSE로 shot을 밀어줌 |
| 글꼴 | Pretendard (OFL, 저장소에 포함). 분석 그림(matplotlib)도 같은 글꼴로 다시 렌더링 | 맑은 고딕 유지 |
| 테마 | 밝은 테마 기본(발표·프로젝터) + 어두운 테마 전환 | 밝은 테마만 |
| 알람 소리 | 기본 꺼짐, 설정에서 켜기 | 경고 시 기본 켜짐 |

## 1. 목적과 사용 상황

- **누가:** 수업 발표의 청중, 그리고 시연에서 역할을 맡는 품질 담당자·공정 엔지니어.
- **어디서:** 1920×1080 프로젝터 또는 노트북. 최소 지원 폭 1024px. 모바일은 대상이 아니다.
- **무엇을:** 과거 생산 데이터를 실제 운영처럼 shot 단위로 재생하면서 다음을 보여 준다.
  - 관리도
  - 제품 위험도
  - 예상 불량 유형
  - 검사 목록
  - **알람과 조치**
- **한계를 숨기지 않는다:** 분석에서 확인한 사실을 화면에 그대로 드러낸다.
  - 시간 순서 검증에서 모델과 최근 불량률 규칙의 성능은 비슷하다.
  - 관리 범위는 '운영 범위(안)'이다.
  - SHAP 상위 변수 상당수는 시기·환경 변수다.

## 2. 설계 원칙

1. **상태 → 조치 → 근거 순서.** 화면 맨 위에서 "지금 문제가 있나"를 답하고, 그다음 "무엇을 하나", 마지막에 "왜 그렇게 판단했나"를 보여 준다.
2. **색은 의미에만.**
   - 상태 색(빨강·주황·노랑·초록)은 알람과 관리한계 이탈에만 쓴다.
   - 데이터 계열은 범주 색을 정해진 순서로 쓴다.
   - 색만으로 의미를 전달하지 않고, 항상 아이콘과 라벨을 함께 둔다.
3. **숫자에는 기준을 붙인다.** "불량률 21%"가 아니라 "최근 50 shot 21% (기준 12%)"처럼 쓴다. 위험 등급 '상'에는 "비용 기준 임계값 이상"을 툴팁으로 단다.
4. **조정 가능한 것과 아닌 것을 나눈다.** 판정 근거(SHAP)와 원인 진단은 '조정 가능 변수'와 '시기·환경 변수'로 나눠 보여 준다(7단계).
5. **알람 피로를 막는다.** 경보는 불량을 실제로 예고하는 규칙만 쓰고(9단계), 중복은 묶고, 빈도를 화면에 보인다.

## 3. 디자인 토큰

`tokens.json`이 유일한 원천이다.
- 대시보드: 빌드할 때 `tokens.css`(CSS 변수)로 바꿔 쓴다.
- 분석 그림: `viz/theme.py`가 같은 파일을 읽는다.
- 컴포넌트는 의미 토큰(`bg.surface`, `text.secondary`, `alarm.critical` 등)만 쓰고 원색 값을 직접 쓰지 않는다.

**위험 등급** (제품):
- 상 `#ec835a`(검정 글자): 보정 확률 ≥ 1/비용 비율, 검사 대상.
- 중: 회색 외곽선.
- 하: 옅은 회색.

**불량 유형** — 모든 화면에서 같은 색을 쓴다(범주 색 1~5번 순서).

| 유형 | 밝음 | 어두움 |
|---|---|---|
| 미성형 | `#2a78d6` | `#3987e5` |
| 박리 | `#eb6834` | `#d95926` |
| 기공 | `#1baf7a` | `#199e70` |
| 변형 | `#eda100` | `#c98500` |
| 기타 | `#e87ba4` | `#d55181` |

**검증 결과** (`tokens.json`의 `$meta.validation`에도 남김)
- 불량 유형 5색은 밝은·어두운 테마 모두 색각 이상(CVD)·정상 시각의 인접 쌍 구분 기준을 통과한다. 가장 가까운 쌍의 ΔE는 9.1(밝음) / 8.4(어두움)이다.
- 밝은 테마의 청록·노랑·분홍은 배경 대비가 3:1 미만이다. 그래서 **불량 유형 색을 쓰는 차트에는 항상 직접 라벨 또는 표 보기를 붙인다.**
- 산점도처럼 모든 쌍이 맞닿는 차트는 3계열까지만 쓴다.
- 글자 대비:
  - 밝은 테마: 본문 19.2:1, 보조 7.7:1, 버튼 흰 글자 5.4:1
  - 어두운 테마: 본문 15.2:1, 보조 9.7:1
  - `text.muted`(3.5:1)는 축 눈금처럼 없어도 되는 정보에만 쓴다.

**차트 색 쓰임**
- 계열: 모델 = 파랑, 규칙 = 주황, 실측 불량률 = 검정 계열 선.
- 관리한계: `chart.reference` 실선. 중심선은 점선.
- 이탈 점: 경고 색 다이아몬드와 "관리한계 이탈" 라벨.
- SHAP 기여: 발산 팔레트(위험 증가 = 빨강 쪽, 감소 = 파랑 쪽, 회색 중립). 막대 끝에 +/− 값을 쓴다.
- 히트맵: 파랑 단색 순차 팔레트.

### 3.2 글꼴·글자

- **글꼴:** Pretendard Variable. npm `pretendard` 패키지를 앱에 포함하고(외부 CDN 없음), 분석 그림용 OTF는 `assets/fonts/`에 넣는다.
- **숫자:** 모두 `tabular-nums`(고정폭 숫자)로 써서 재생 중에 자릿수가 흔들리지 않게 한다.
- **굵기:** 400·600·700 세 가지만 쓴다.

| 이름 | 크기/줄 높이 | 굵기 | 쓰임 |
|---|---|---|---|
| display | 32/40 | 700 | KPI 핵심 숫자 |
| h1 | 24/32 | 700 | 화면 제목 |
| h2 | 18/26 | 700 | 카드 제목 |
| h3 | 15/22 | 600 | 소제목·표 머리 |
| body | 14/20 | 400 | 본문·표 |
| small | 13/18 | 400 | 범례·보조 설명 |
| caption | 12/16 | 400 | 축 라벨·각주 (최소 크기) |

### 3.3 간격·모양·움직임

- **간격:** 4px 단위(0, 2, 4, 8, 12, 16, 20, 24, 32, 40, 48, 64).
  - 카드 안쪽 여백 16px(넓은 화면 20px)
  - 카드 사이 16px
  - 페이지 여백 24px
- **모서리:** 4(배지·막대 끝), 8(버튼·입력), 12(카드), 999(알약 모양).
- **그림자:**
  - 카드는 그림자 없이 테두리만 쓴다.
  - 팝오버 `0 4px 16px / 8%`
  - 토스트 `0 8px 24px / 14%`
  - 모달 `0 16px 48px / 20%`
- **움직임:**
  - 120ms(작은 상태 변화), 200ms(패널 열기), 320ms(드로어).
  - 재생 중 차트에 점이 추가될 때는 애니메이션을 쓰지 않는다(초당 10 shot에서 깜빡임 방지).
  - `prefers-reduced-motion`이면 모든 전환을 0ms로 한다.
- **레이아웃:** 12열 그리드, 간격 16px.
  - 상단 바 56px
  - 왼쪽 탐색 72px
  - 재생 조작 바 64px
  - 경고 배너 48px
- **기준 해상도:** 1920×1080. 1280px에서 2열, 1024px에서 1열로 접는다.

### 3.4 차트 표시 규칙

- 선 두께 2px, 점 8px(바탕색 2px 테두리), 막대 끝 모서리 4px, 막대 사이 2px.
- 격자는 값 축에만 가는 선으로 긋는다. 이중 축은 쓰지 않는다. 크기가 다른 두 값은 위아래 두 차트로 나눈다.
- 계열이 2개 이상이면 범례를 둔다. 4개 이하는 선 끝에 직접 라벨도 붙인다.
- 모든 차트에 마우스 툴팁을 단다. 시계열은 십자선을 쓴다.
- 모든 차트에 '표로 보기' 전환을 둔다.
- 부제목의 숫자는 데이터에서 계산한다(고정 문구로 주장하지 않는다).

## 5. 화면 구성

왼쪽 탐색은 4개 화면과 설정이다. 재생 조작 바와 경고 배너는 모든 화면 위에 고정한다.

```
┌ 상단 바: DieCast-QA · 시나리오 [유형2 · 구간 5부터 · 경보 시 재학습] · ● 재생 중 shot 1,240/1,964 · 🔔3 ┐
├ 재생 바: ▶ ❚❚  ◀ ▶  속도 [1][2][5][10]  ━━━━━━━●━━━━━━  ┤
├ 경고 배너(경고가 있을 때만): ⬣ 경고 · 불량률 CUSUM 경보 (shot 1,212) · 다음 50 shot 전수검사 [조치 보기] ┤
```

### ① 운영 현황 (기본 화면)

```
[KPI] 최근 50 shot 불량률 | 활성 알람 | 검사 비율·누적 포착률 | 누적 비용 vs 전수검사 | 진행 shot
┌ p-chart (50 shot 부분군) ──────────────┐ ┌ 알람 피드 ───────┐
├ 불량률 CUSUM (상·하측) ────────────────┤ │ 경고/주의/정보 최근 │
├ 공정 변수 4개 (관리 범위 띠) 작은 차트 ─┤ ├ 위험 제품 상위 5 ─┤
└──────────────────────────────────────┘ └──────────────────┘
```

- 공정 변수는 관리 범위(안)가 있는 변수(유형 1: 사이클 타임·비스킷 두께, 유형 2: 냉각수 온도·3단 사출 속도·비스킷 두께)를 먼저 보여 주고, 나머지는 선택해서 본다.
- 경보 지점에는 차트 위에 세로선과 배지를 표시한다.

### ② 제품·검사


## 6. 알람 시스템

규칙과 조치는 9단계 연구 결과(`results/improve/alarms_ocap.csv`)를 그대로 쓴다.

| 등급 | 발생 조건 | 근거 (9단계) | 화면 표시 | 즉시 조치 | 해제 |
|---|---|---|---|---|---|
| 경고 | 불량률 CUSUM 상측 경보 (k=0.25, h=8, 직전 200 shot 기준) | 경보 뒤 50 shot 불량률이 평균의 1.41배, 불량 shot의 26% 포함 | 배너 고정, 벨 숫자, 차트 세로선, (설정 시) 소리 | 다음 50 shot 전수검사, 원인 진단 표시, 모델 재학습 | 50 shot 동안 새 경보 없음 |
| 주의 | 위험도 ≥ 비용 기준 임계값인 제품 | 같은 검사량에서 무작위의 약 2배 불량 포착(8단계) | 위험도 표 강조, 토스트(묶음) | 해당 제품 검사, 예상 유형 점검 항목 | 검사 완료 |
| 정보 | 관리 범위(안) 밖 운전 지속: 최근 20 shot 중 80% 이상 | 불량 예고력은 약함(0.8~1.6배) → 개선 대상 표시용 | 공정 변수 차트 배지, 알람 센터 | 설정 조정 검토, 실험 계획 후보 | 최근 20 shot 중 범위 밖 50% 미만 |
| 기록 | 공정 변수 급변 (직전 50 shot 중앙값 ± 3.5σ) | 불량을 예고하지 못함 | 알람 센터에만 | 없음(원인 진단 기록) | — |

- **알람 하나의 생애:** 발생 → 확인(사용자가 '확인') → 조치 중(체크리스트 진행) → 해제(조건 충족 시 자동, 이력 보존).
- **원인 진단 패널** (경고 상세):
  - 그 시점에 관리 범위 밖인 변수 목록
  - 최근 50 shot의 불량 유형 구성 변화. 예: 유형 2는 경보 뒤 기공 비중 32% → 47%.
  - 늘어난 유형의 점검 항목(7단계 체크리스트)
- **알람 피로 방지:**
  - 같은 규칙·같은 변수는 쿨다운(경고 50 shot, 정보 20 shot) 안에서 하나로 묶는다.
  - 주의 토스트는 10 shot당 1개까지만 띄운다.
  - '100 shot당 알람 수'를 알람 센터에 늘 표시한다.
- **검사 피드백 가정:** 선별검사로 운영하면 검사하지 않은 제품의 결과를 모른다(8단계). 그래서 재생 화면은 '전수검사 결과를 안다'는 분석 가정을 쓰고, 설정 화면에 이 가정을 명시한다.

## 7. 재생 시뮬레이션

- **시나리오:** (시작 구간) × (재학습: 없음 / 50 shot마다 / 관리도 경보 시)를 백엔드가 미리 계산해 둔다(11단계 스크립트).
  - 시작 구간 후보: 유형 1 구간 2·3, 유형 2 구간 5·7. 시작 이전 데이터가 충분한 구간이다.
  - 대시보드 모델(`models/*.joblib`)은 시작 이전 데이터로만 학습한다(11.1).
- **진행:** 브라우저 타이머가 속도(1~10 shot/초)에 맞춰 shot을 하나씩 공개한다.
  - 데이터는 200 shot 단위로 미리 받아 둔다.
  - 정지·되감기·한 shot 이동이 즉시 반영된다.
  - 같은 시나리오는 항상 같은 결과를 낸다(seed 42).
- **판정 근거(SHAP):** 미리 계산한 값을 쓴다. 재학습 옵션이 켜져 있으면 모델이 바뀌므로 SHAP 대신 재학습 시점의 변수 중요도를 보여 준다(11.3).
- **키보드:** Space 재생/정지, ←/→ 한 shot, Shift+←/→ 50 shot, 1·2·5·0 속도.

## 8. 기술 구성과 API 계약

```
app/
  api/  FastAPI — 분석 결과·시나리오 제공 (읽기 전용 JSON)
  web/  Next.js (App Router, JavaScript) — tokens.css + CSS Modules, ECharts
```

| 엔드포인트 | 응답 |
|---|---|
| `GET /api/meta` | 제품 유형·구간, 시나리오 목록, 변수 라벨·그룹, 비용 비율, 토큰 버전 |
| `GET /api/scenarios/{id}` | 시작 shot, 길이, 모델 학습 기간, 재학습 시점 |
| `GET /api/scenarios/{id}/shots?offset=&limit=` | shot마다: order·구간·shot 번호, 공정 변수, 제품 2개의 확률(원·보정)·위험 등급·예상 유형 확률·SHAP 상위·실제 불량/유형 |
| `GET /api/scenarios/{id}/limits` | p-chart·CUSUM 관리한계(시작 이전 데이터로 계산, 3단계 `fit`) |
| `GET /api/scenarios/{id}/alarms` | 알람 이벤트: shot, 등급, 규칙, 값, 근거, 조치, 원인 진단 |
| `GET /api/summary` | 분석 요약 화면용 정적 결과(파레토, 관리 범위, 점검 항목, 성능, 비용, 개선 방안) |

- 검사 목록과 비용은 사용자가 비용 비율을 바꿀 때마다 바로 반응해야 하므로 브라우저에서 계산한다.
  - **검사 기준(구현에서 바꿈):** 50 shot 로트마다, 재생 중 이미 결과를 안 과거 제품에서 총비용이 가장 작은 위험도 임계값을 쓴다(8단계와 같은 방식).
  - 처음 200개 제품까지는 보정 확률 ≥ 1/비율을 쓴다.
  - 바꾼 이유: 시작 시점의 보정은 시기가 바뀌면 낮게 치우친다. 실제로 구간 4로 보정한 확률이 불량률 26%인 구간 5에서 9% 수준에 머물렀다.
  - 과거 결과가 '전부 검사'를 고르면 전수검사 모드로 표시하고, 제품별 '주의' 알림은 띄우지 않는다.
- 백엔드는 시나리오를 파일로 미리 만들어 두고 읽기만 한다. 실시간 학습은 하지 않는다.

## 9. 접근성·품질 기준

- 글자 대비는 WCAG AA(본문 4.5:1, 큰 글자·아이콘 3:1)를 지키고, 상태는 색 + 아이콘 + 라벨로 표시한다.
- 모든 조작은 키보드로 할 수 있다. 포커스 링은 2px `focus.ring`이다.
- 모든 차트에 '표로 보기'를 두고, 불량 유형 색 차트에는 직접 라벨을 붙인다.
- 한국어 라벨을 기본으로 하고, 변수 원래 이름(영문)은 툴팁에 함께 보인다.
- 성능 목표: 초당 10 shot 재생에서 프레임 저하가 없을 것(차트는 증분 추가, 표는 최근 100행만 렌더링).

## 10. 구현 순서 (11단계, 기획서 11.3의 단계적 확장)

1. **1차:** 토큰·기본 컴포넌트, 재생 엔진, 운영 현황(p-chart, CUSUM, KPI), 위험도 표, FastAPI 기본 엔드포인트.
2. **2차:** 예상 유형·판정 근거, 검사 목록·비용, **알람 시스템**(배너·토스트·알람 센터·조치 체크리스트).
3. **3차:** 재학습 옵션 시나리오, 분석 요약 화면, 어두운 테마, 분석 그림을 확정 토큰으로 다시 렌더링.
